# Brownfield 演示：为存量系统补写规范（第 7.4 节）

> 复现《SDD 实战：规范驱动开发之道》**第 7.4 节**的完整四步法。
> 书中讲的是"如何给没有规范的存量系统补规范"，但要演示就得有一个存量系统 ——
> 所以本目录**刻意构造**了一个具备存量系统全部病症的遗留模块，然后严格按书中流程处理它。

## 为什么要有这个演示

书里 7.4.1 用四个特征描述存量系统，这套流程如果只写在文档里，
读者无法判断自己是否真的理解了"现有行为 ≠ 正确行为"这个关键判断。
本演示把四步法**做成可执行、产物可对照**的流程。

## 存量系统样本长什么样

`legacy/` 下两个模块，对照书中的四个特征：

| 书中特征 | 样本中的体现 |
|---|---|
| **逻辑成谜** | 重试为什么 3 次、超时为什么 30s、限流后为什么固定等 60s —— 无任何说明 |
| **需求散佚** | 没有 `proposal.md`，需求只存在于代码与口头约定 |
| **架构漂移** | `collect()` 既采集又拼文本；`build()` 生成完直接发邮件 |
| **测试薄弱** | 覆盖率 0%，任何修改都伴随回归风险 |

另有隐性决策：`sorted()` 隐式决定输出顺序、`dict.get(key, 0)` 让"字段缺失"与"真为 0"无法区分。

## 四步法与产物对照

```bash
cd brownfield-demo
python -m tools            # 走完四步，打印每步产物
python -m tools analyze    # 第一步：逆向工程（只给客观事实）
python -m tools contract   # 第二步：生成接口契约草稿（标注需人工判断）
python -m tools prompts    # 打印书中那段逆向工程 Prompt 原文
python -m pytest -q        # 50 个测试
```

| 步骤 | 书中要求 | 本演示的产物 |
|---|---|---|
| **一 逆向工程** | 提取对外接口、依赖、异常、行为边界 | `tools/brownfield.py` 用 AST 客观提取；**故意不猜**魔法数字的含义（猜错会误导审查），只给出源码行让人看 |
| **二 规范化** | **必须人工介入**，因为"现有行为 ≠ 正确行为" | `specs/contracts/legacy-baseline.md`：把每项隐性决策写成 `现有行为 / 判定 / 定稿行为` 三列，逐条给出保留或修正及理由 |
| **三 补写测试** | 验证现有行为，并暴露未覆盖的边界 | `tests/test_legacy_characterization.py`（固化现有行为）+ `tests/test_legacy_fixed_contract.py`（验证修正后行为） |
| **四 锁定基线** | 测试全绿后连同规范一起提交 | 契约标注"已采纳"；此后该模块**先更新规范，再改代码** |

## 第二步到底判断了什么（这是演示的核心）

`legacy-baseline.md` 里 14 条判定，几条有代表性的：

| 现有行为 | 判定 | 理由 |
|---|---|---|
| 重试 3 次、间隔 5s | **保留** | GitHub 偶发 5xx，3 次足够；间隔 5s 避免放大故障 |
| 限流后固定 `sleep(60)` 再重试 | **修正** | 固定等 60s 是错的：应读 `X-RateLimit-Reset` 算真实等待，且必须设上限（否则挂死定时任务） |
| `collect()` 顺手把结果拼成文本返回 | **修正（职责越界）** | 采集层只返回结构化记录；文本拼接属于生成层 |
| 详情回查失败时 `except: pass`，统计字段留 0 | **修正** | **静默填 0 让"未知"与"真为 0"无法区分**；改为 `None` + 警告日志 |
| `check_token()` 非 401 错误时 `return True` | **修正（掩盖失败）** | 只有 200 才返回 True |
| 超 60 字符截断、单成员最多 200 条 | **保留** | 实践中稳定；但必须变成具名常量并写入契约 |
| 按作者名 `sorted()` | **修正** | 排序是隐式副作用，必须**显式声明**为契约行为 |
| 生成与发信耦合在一个类里 | **修正（职责越界）** | `build()` 只生成；发信交给 `send()`，凭据由调用方注入 |

> 修正版实现落在 `legacy_fixed/`，与 `legacy/` 并存，便于对照。
> **未变更的模块按 7.4.2 节"逐步收缩"策略不处理** ——
> 不追求 100% 覆盖，低频变更模块保持原样。

## 一个值得注意的细节

`legacy/` 与 `legacy_fixed/` 是**两套并存**的代码，这不是冗余，而是演示的需要：
- `legacy/` 用来跑**特征化测试**（记录"改之前是什么样"）
- `legacy_fixed/` 用来跑**契约测试**（验证"改之后符合规范"）

真实项目中，第四步完成后应当删除旧实现；这里保留是为了让对照关系可查。

## 与主项目的关系

这一步的方法论是通用的：主项目 `sdd-daily-report` 走的是 **Greenfield**（从零建规范），
本目录走的是 **Brownfield**（给已有代码补规范）。两者共用同一套契约格式与测试纪律。

## 测试

```bash
python -m pytest -q     # 50 passed
```

- `test_legacy_characterization.py`（6 个）：固化存量行为，含把"生成与发信耦合"记为反面样本
- `test_legacy_fixed_contract.py`（31 个）：按定稿契约逐条验证修正版
- `test_brownfield_tooling.py`（13 个）：分析器与提示词，含"书中 Prompt 四项要求逐条对照"

## 依赖

**零第三方依赖** —— 逆向工程分析器只用标准库 `ast`。
这是刻意的：工具要能对任意存量仓库直接跑起来，不该要求先装一堆包。
除了测试需要 `pytest`，运行 `python -m tools` 只需标准库。
