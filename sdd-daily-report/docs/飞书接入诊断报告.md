# 飞书接入诊断报告（实测）

> 用真实应用凭据 `cli_xxxxxxxxxxxxxxxx` 对飞书开放平台做的**只读探测**结果。
> 探测工具：`verify_connectivity.py --lark`；探测时间：2026-09-26。

## 一、错误码判读表（实测确认）

飞书对三类问题返回不同错误码，可据此精确定位，**不必猜**：

| 错误码 | 含义 | 推论 |
|---|---|---|
| `99991672` | 应用缺权限 | **端点路径已解析成功**，只差开通 scope |
| `99992402` | 请求体字段校验失败 | **端点路径已解析成功**，且**权限已开通** |
| `230006` | 机器人能力未启用 | 应用配置问题，非权限问题 |
| `232034` | 应用在租户内不可用/未激活 | 应用未发布或未启用机器人能力 |
| `10002` / 404 | 资源或路径不存在 | 端点可能写错 |

**重要教训**：`99992402` 的完整响应里带 `error.field_violations`，会逐字段说明缺什么。
早期版本的工具只打印 `msg`（"field validation failed"），把这段关键信息截断了，
导致误判为"无法反推参数格式"。**排查时必须读完整响应体。**

## 二、逐项实测结论

| 接口 | 端点 | 结果 | 状态 |
|---|---|---|---|
| 任务列表 | `GET /task/v2/tasks` | `code=0`，返回 `{has_more, items, page_token}` | ✅ **可用**（应用名下暂无任务数据） |
| 通讯录 | `GET /contact/v3/users` | `code=0 success` | ✅ **可用** |
| 群列表 | `GET /im/v1/chats` | `code=0 success`（机器人已激活；当前 0 个群） | ✅ **可用** |
| 发消息（单聊） | `POST /im/v1/messages` + `receive_id_type=open_id` | `code=0 success` | ✅ **可用，已实测发送成功** |
| 建群 | `POST /im/v1/chats` | `99991672` 缺 `im:chat:create` | ⚠️ 需补权限（有替代方案，见下） |
| 群消息采集 | `GET /im/v1/messages` | **已打通**：重新发布版本后应用身份可用，实测取到 7 条真实群消息 | ✅ **可用** |
| 考勤 | `POST /attendance/v1/user_tasks/query` | **格式已校准**：返回业务级 `1220001 employeeNos is empty` | ✅ 格式正确（该租户无考勤数据） |

### 关键突破：单聊推送绕开了建群权限

机器人激活后，`GET /im/v1/chats` 返回 0 个群 —— 机器人不在任何群里，
而建群需要 `im:chat:create`（当前未开通）。

**替代方案（已实测成功）**：改用 `receive_id_type=open_id` 直接向用户发单聊消息。
这条路径**只需要 `im:message:send_as_bot`**，不需要任何群管理权限。

已在 `LarkConfig` 中新增 `receive_id_type` 字段（默认 `chat_id`，向后兼容），
`config.github.yaml` 中设为 `open_id` 并填入用户 `open_id`。

真实推送结果：

```
推送：email=成功、lark_bot=success
✓ 飞书推送成功  receive_id_type=chat_id  target=oc_5b146672...  attempt=1
```

**日报已同时投递到 QQ 邮箱与飞书群**。

### 群消息采集：已打通（2026-09-26）

权限面板显示 `im:message.group_msg` 的权限类型为「用户身份」，
我最初据此判断"应用身份永远拿不到"。**这个判断过于绝对** ——
**重新发布版本后，应用身份也能正常调用**：

```
✓ 群消息  code=0  success
✓ 取到 7 条真实群消息
```

因此 `auth_mode` 默认保持 `app`（无需用户手动 OAuth），
用户身份路径（`UserTokenManager`，支持授权码换取 + 落盘 + 自动刷新）作为备用保留。

接真实群消息后还暴露并修正了两处**数据质量缺陷**：

| 缺陷 | 现象 | 修正 |
|---|---|---|
| 系统消息被当正文 | `msg_type='system'` 的入群提示（`{from_user} invited ...`）被收进日报 | 跳过系统消息，实测 7 条降到 3 条 |
| `sender` 恒为 unknown | 旧代码取错了字段 | 正确结构是 `sender.{id, id_type, sender_type}`；机器人消息 `id` 是 `app_id`，真人消息是 `open_id` |

两条均已加测试锁定。

### 关于 `project_id` 的修正

此前担心"`/task/v2/tasks` 要的是任务清单 GUID、而配置里写 `project_id` 类型对不上" ——
**实测证明这个担心是错的**：`project_id` 参数被正常接受，换一个不存在的 ID 也不报错。
当前返回 0 条任务，是因为该应用名下**确实没有任务数据**，不是参数问题。

## 三、如仍需群推送

若希望日报推到**群**而不是单聊，需补一个权限：

```
https://open.feishu.cn/app/cli_xxxxxxxxxxxxxxxx/auth?q=im:chat:create&op_from=openapi&token_type=tenant
```

开通并发布后，把 `config.github.yaml` 的 `receive_id_type` 改回 `chat_id`，
并填入群的 `chat_id`（可用 `GET /im/v1/chats` 查询）。

**但这不是必须的** —— 单聊推送已验证可用。

## 四、考勤接口：已解决（依据官方文档校准）

### 结论

**请求格式已校准通过。** 校准判据：错误码从**格式级** `99992402 field validation failed`
变为**业务级** `1220001 employeeNos is empty`。

### 根因：三处参数与官方文档不符

查飞书官方文档后确认，`POST /attendance/v1/user_tasks/query` 的参数分两处承载，
且日期是**整数**类型的 `YYYYMMDD`：

| 参数 | 位置 | 类型 | 初版实现 |
|---|---|---|---|
| `employee_type` | **query string** | string | ❌ 放在请求体 |
| `user_ids` | 请求体 | array | ✅ 正确 |
| `check_date_from` | 请求体 | **integer** `20260424` | ❌ 传 ISO 字符串 |
| `check_date_to` | 请求体 | **integer** `20260424` | ❌ 传 ISO 字符串 |

这也解释了此前那组"自相矛盾"的探测结果：参数走 query 时 `employee_type` 被读到、
走 body 时 `user_ids`/日期被读到，正是因为**它们本就该分处两地**；
而当时把日期传成字符串，所以即使位置对了仍报字段校验失败。

### 为什么之前 20+ 次试错都没成功

因为我在**猜**而不是**查**。错误码 `99992402` 只说"字段校验失败"，
在没有文档的情况下，参数的位置、名称、类型组合空间太大
（4 个参数 × 3 种位置 × 多种类型），试错效率极低。

**教训**：遇到第三方 API 的字段校验错误，应当**先查官方文档**，
而不是靠错误信息反推参数格式。

### 顺带修复的缺陷

飞书在 HTTP 400 时**同样返回结构化 `code`/`msg`**，而早期实现只抛 `"HTTP 400"`，
把 `employeeNos is empty` 这类可用于定位问题的业务提示丢掉了。现已原样透传。

### 覆盖测试

`tests/test_attendance.py` 中新增三条格式契约测试锁定请求构造：
`employee_type` 走 query、日期为整数 `YYYYMMDD`、`user_ids` 走请求体。
