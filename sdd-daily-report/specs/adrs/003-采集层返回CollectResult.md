# ADR-003：采集层返回 CollectResult

## 状态
已采纳

## 背景
v1.0 的采集层接口定义为 `collect(...) -> list[Record]`。在实现第 7 章 v1.1 迭代时发现：
当某个数据源采集失败（API 超时、限流、Token 失效）时，采集层返回空列表，
这与"该数据源当日确实没有数据"在类型上完全无法区分。

然而 proposal.md §3.2 明确要求：
"采集失败的数据源需要在日报中显式标注'数据获取失败'，严禁静默跳过。"

空列表无法承载"失败原因"，因此这不是一个代码 bug，而是**接口契约的缺陷**。

## 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| 返回 list，失败时抛异常 | 不改类型，改动最小 | 调用方需用 try/except 区分，与"优雅降级"策略冲突（一个数据源失败会跳出汇总流程） |
| 返回 list，失败返回空列表（现状） | 无需改动 | **无法区分"无数据"与"采集失败"，直接违反 proposal.md §3.2** |
| 返回 CollectResult | 显式区分成功/失败并携带 error_message；天然支持优雅降级 | 需修改三个采集模块与其调用方、测试 |

## 决策
采集层统一返回 `CollectResult[T]`：

```python
CollectResult[T]:
  success: bool
  records: list[T]
  error_message: str | None
```

## 理由
1. 这是"规范驱动"的直接体现：proposal.md 的验收标准要求区分失败与无数据，
   代码层无法满足时应回溯修改 design.md，而不是在代码里打补丁绕过。
2. 与 design.md §6.1 的优雅降级策略一致——每个数据源独立返回成功/失败，
   主流程可继续用其余数据源生成日报。
3. 失败原因（error_message）可直接写入日报标注与 JSON 日志，
   满足"任何失败都必须有日志记录"的关键原则。
4. 该变更属于架构变更（起点 design.md），影响链为
   design.md → tasks.md → 代码 → 测试，因此同步新增 Task 11 并修改 Task 3~Task 6、Task 10。
