# ADR-004：展示层技术栈与设计系统来源

## 状态
已采纳（v1.2 需求变更新增）

## 背景

`proposal.md` §2.1 新增"本地 Web 展示页"后，架构上必须补两个决策：

1. **展示层用什么跑起来**——新增 Web 框架，还是复用现有依赖集合？
2. **视觉从哪来**——配色、字号、间距、状态色由谁定义？

这两个问题看似是"实现细节"，但它们直接决定 `proposal.md` §2.3 技术约束里的两条是否继续成立：
"复用团队现有技术栈"与"不需要常驻后台服务"。因此按《SDD 实战》表 7-2，这属于**需求变更**带出的
架构决策，起点是 `design.md`，需要落成 ADR。

## 选项

### 决策一：展示层的运行时依赖

| 选项 | 优点 | 缺点 |
|---|---|---|
| 新增 FastAPI + uvicorn | 端点声明与参数校验开箱即用，将来扩展接口省事 | 一次性引入 29 个分发包（fastapi/starlette/pydantic/anyio/uvicorn…），为 3 个只读端点撑起整套 ASGI 栈；把 Cron 链路的依赖集合从 3 个包扩大一个量级，违反 §2.3"复用团队现有技术栈" |
| 新增 Flask | 比 FastAPI 轻，路由与模板现成 | 仍是新增运行时依赖；本项目只需"读库→出 JSON/静态文件"，Flask 提供的路由/会话/模板能力绝大部分用不上 |
| Python 标准库在局域网内做 HTTP 服务 | 零新增依赖，离线可用，Cron 链路不受影响 | `http.server` 只给基础能力：路由、参数解析、错误码、静态文件都要自己写；并发是单线程 `HTTPServer`（对单机单用户够用） |

### 决策二：设计系统来源

| 选项 | 优点 | 缺点 |
|---|---|---|
| `ant`（OpenDesign 内置 153 套之一） | 企业级、数据密集，正是"日报 + 考勤 + 提交统计"这类页面的母语；含 56 个来源可核对的令牌（`sourceBackedTokens: 56`） | `--accent` 是红色（`#d32029`），与"危险色"易混，必须严格按语义分派 |
| `wechat` | 中文语境亲切，微信生态观感 | 偏消费端社交气质，与"团队 Leader 看数据"的场景不贴 |
| `xiaohongshu` | 视觉冲击强，展示效果好 | 偏内容社区风格，数据密度低，表格与统计不友好 |
| 由 AI 临时定配色与字号 | 零成本，随时可改 | **不成体系**：没有令牌、没有出处的色值，改一处颜色要全文搜替；无法向他人解释"为什么是这个红" |

## 决策

1. **展示层运行时依赖为零新增**：用 Python 标准库 `http.server` + `sqlite3` + `json`，
   前端为静态 `HTML + CSS + 原生 JS`，不引入任何 Web 框架，不需要构建步骤。
2. **视觉采用 OpenDesign `ant` 设计系统的令牌**，机器可读原件为
   `design-tokens.json`（`format: od-design-tokens/v1`，56 个令牌），
   按 `design.md` §6.5(4) 的语义映射表取用。

## 理由

1. **§2.3 技术约束优先于实现便利**：`proposal.md` 明确"复用团队现有技术栈"且
   "不需要常驻后台服务"。展示页是"按需启动、用完即关"的旁路，为一个旁路引入整套 ASGI 栈，
   是拿架构复杂度换开发便利，与 `design.md` §1"选择能满足需求的最简架构"的黄金法则冲突。
2. **依赖扩张的真实代价已被验证**：本复现环境实测安装 FastAPI 会拉入
   29 个分发包（`annotated-doc`、`annotated-types`、`anyio`、`click`、`fastapi`、`h11`、
   `idna`、`opentelemetry-api`、`pydantic`、`pydantic-core`、`starlette`、`typing-extensions`、
   `typing-inspection`、`uvicorn` 等）。对一个 3 端点的只读服务，这不是"技术先进"，
   而是把供应链面积放大了好几倍。
3. **零依赖不等于不可测**：展示层的**逻辑**（读库 → 视图模型 → 状态判定）放在
   `webview/views.py`，不依赖任何 HTTP 设施，可直接单测；`webview/app.py` 只剩
   "把 HTTP 请求翻译成 views 调用"的薄壳。这与 `kb-search` 项目里
   "把逻辑抽到框架无关的 `handlers.py`、`api.py` 仅作 30 行适配器"是同一手法。
4. **设计令牌要选"有出处"的**：`ant` 的 56 个令牌在 `source/token-contract.report.json` 中
   报告为 `sourceBackedTokens: 56`、`score: 100`、`grade: excellent`、`recommendRebuild: false`，
   即每个令牌都能追到来源，而不是生成的近似值。这使"配色"从主观判断变成可审查的契约。
5. **同一设计系统内部存在口径冲突，必须指定唯一来源**：实测 `ant` 目录下
   - `design-tokens.json` / `tokens.css`：`--accent: #d32029`、`--fg: #1f1f1f`；
   - `DESIGN.md` 正文：`Primary: #1677FF`、`Text: #111827`、字体族写 `Plus Jakarta Sans`。

   两者不一致。以**机器可读的令牌文件**为准，理由是它带 `layer`（`A1-identity` 等）、
   `confidence` 与 `sourceBacked*` 统计，可被程序校验；而 `DESIGN.md` 的色值段落是
   模板化的通用占位文本，同一份文件里连字体族（`Plus Jakarta Sans`）都与 `tokens.css`
   的 `Ant Sans / Alibaba PuHuiTi` 不一致，不具备事实来源资格。此冲突在此登记，
   以免后续维护者按 `DESIGN.md` "修正"回 `#1677FF`。

## 补充记录（v1.2 落地阶段，ADR 只追加不修改）

本节记录落地时发现的三个问题与处置，**不修改上文决策**。

### 补充一：`status` 由三态改为四态（规范缺陷回溯）

设计稿交付后暴露出 §3.2 原推导规则的一处缺陷：它把"`sources` 为空"并入 `failed`。
后果是 v1.2 之前生成的历史日报（未持久化 `sources`）会在列表上顶着"数据源全部失败"的徽标，
点进详情页却一个失败 chip 都没有 —— **把"没记录"说成"全部失败"是撒谎**。

处置：按《SDD 实战》图 7-8 的"有失败 → 判定失败类型？→ 规范缺陷 → 回溯更新规范"分支，
在 `design.md` §3.2 拆出第四态 `unknown`（页面文案"未记录数据源状态"，用中性色），
并同步 `contracts/data-models.md` §3、`contracts/api-spec.yaml` 的 enum、
`proposal.md` §3.1 与 `tasks.md` Task 12 的验收标准。**这是规范先行、代码跟随的一次实际执行。**

### 补充二：字体族有意偏离令牌（落地环境所限）

令牌原文的字体族为 `"Ant Sans","Alibaba PuHuiTi",Inter,Arial,sans-serif`，
但落地环境未安装前两者，直接照抄会静默回退到 `Arial`，失去中文字形优化。
因此展示层改用系统字体栈 `ui-sans-serif, system-ui, -apple-system, "Segoe UI", "PingFang SC", …`，
**语义不变**（无衬线正文体），且不引入任何字体文件下载（§6.5(3) 零新增依赖）。
其余 55 个令牌一律照抄，不做同类偏离。

### 补充三：字号收口

设计稿在 6 处使用了令牌阶梯之外的 `13px`，而它自己的字号面板同时写着"12px — 段标题"。
按"令牌引用语义、不新增字号"的约束，落地时统一收进 `--text-xs`（12px），
不把 `13px` 提升为新令牌。

### 补充四：设计稿的"评审用"部分不进入产品

OpenDesign 交付的 `index.html` 是**设计稿**，含三块自我说明内容：评审导航（列表/详情/异常态/规范四视图切换）、
设计规范面板、异常与空态独立小样页。这三块用于评审与交付，**不进产品**：
落地时拆分/合并为 `webview/static/index.html` + `app.css`，只保留"列表页 + 详情页"两级真实界面，
其余异常状态就地呈现在真实语境中（对应 `proposal.md` §2.1"页面只做两级浏览"）。
