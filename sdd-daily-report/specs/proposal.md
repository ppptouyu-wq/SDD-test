# 智能日报生成器

## 1. 背景与目标

### 1.1 背景
目前，团队成员每天需要耗费 15~30min 手动撰写日报，内容涵盖当日代码提交、任务进展及协作沟通情况。这一过程不仅重复低效，且常因遗忘导致信息缺失。
另外，团队 Leader 需要掌握成员的工作动态，但人工撰写的日报往往信息密度低、格式参差不齐，严重影响了阅读体验与管理效率。

### 1.2 目标
构建一个自动化工具，旨在从团队现有的协作平台中抓取当日工作数据，自动生成结构化日报，并精准推送给相关干系人。

### 1.3 目标用户
- 主要用户（数据生产者）：5 ~ 15 人的研发团队核心成员
- 主要读者（数据消费者）：团队 Leader 及项目经理

## 2. 功能范围

### 2.1 做什么（本期）

#### 数据采集
- 对接 GitHub/GitLab，获取当日代码提交记录（含 Commit Message 及变更统计）
- 对接飞书/Jira，抓取当日任务状态流转（如新建、进行中、已完成）
- 从飞书群消息中提取与项目强相关的讨论摘要
- 采集飞书考勤数据（新增 v1.1）

#### 日报生成
- 将采集数据按"代码提交→任务进展→协作沟通"的逻辑进行三段式编排（v1.15 起邮件渠道另作收敛：只留"代码提交→任务进展→考勤"，协作沟通待在 Markdown 与展示页，见 §3.1）
- 为每位成员生成独立的日报段落
- 输出 Markdown 格式（支持无缝转换为 HTML 邮件）

#### 推送通知
- 由调度器按需触发（默认每日 18:00）。**产品本身不限制生成日期**：双休日与
  法定节假日同样可以正常生成并推送日报（变更 v1.4）
- 通过 SMTP 服务向团队 Leader 发送 HTML 格式日报
- 通过飞书机器人将 Markdown 格式日报推送至团队群组

#### 本地 Web 展示页（新增 v1.2）
- 提供本地网页入口，供团队 Leader 在浏览器中查看已生成的日报
- 页面只做"日报列表 → 日报详情"两级浏览：首页按日期倒序列出数据库中的日报，
  点击任意一条进入详情页，用与前两个推送渠道一致的排版展示当日完整日报
- 不做任何写入操作：页面只能读，不能编辑、补充、删除或重新生成日报
- 三种异常状态必须在页面上显式区分，严禁与"当日确实无数据"混淆：
  数据源采集失败、考勤数据不可用、指定日期无日报记录
- 日报状态徽标必须区分四种情况：数据源正常、部分数据源失败、数据源全部失败，
  以及 v1.2 之前生成的历史日报"未记录数据源状态"——**不得把"没记录"误报成"全部失败"**

#### 持续集成与镜像交付（新增 v1.12）
- 每次推送或开 PR，自动在流水线上跑三个项目的测试与规范治理检查（生成—评审、团队实践、
  规范兑现度），任一环节红则整条流水线就此停下，**不构建、不推送任何镜像**
- 打 `v*` 版本标签时，在流水线里构建容器镜像并推送到镜像仓库（GitHub Container Registry），
  镜像带三种标签：提交哈希（可追溯、不可变）、版本号、`latest`
- 镜像本身不含任何凭据与本地数据；流水线全程只跑"不触网"的演示模式，
  不向真实飞书群或真实邮箱发信

#### 交付流水线现状如实呈现（新增 v1.13；v1.14 增"真实运行结论"）
- 邮件日报在「今日工程进展」之后单列一段，用一条链路说清交付走到了哪一步
- 板块里的每个状态都必须能由收件人**当场复核**：文件类事实读仓库，运行结论读公开接口；
  读不到就写"未采集"并写明原因，**绝不**把没验证过的事写成"已跑通"
- v1.14 补齐"最近一次运行"这一项：结论不再一律留空，而是读默认分支最新提交的
  检查结果（Check Runs）得出，并附提交哈希，收件人可据此原样回查

### 2.2 不做什么（本期明确排除）
- 不做智能摘要和 AI 总结（本期仅做数据清洗与整理，不涉及语义理解）
- 不做移动端 App（v1.2 的展示页是**桌面浏览器单页**，viewport 适配下限 1024px，不做手机端布局）
- 不做历史日报的搜索、筛选、分页控件与统计图表分析（v1.2 展示页只做日期倒序列出与按日期浏览，不提供搜索框、不画任何图表）
- 不做个人日报的手动编辑与补充功能（v1.2 展示页为**只读**，无任何写接口）
- 不做支持多团队隔离/多租户架构（v1.2 展示页只展示单团队数据，不做团队切换）
- 不做登录、账号与权限体系（v1.2 展示页只监听本机回环地址 `127.0.0.1`，不对外网暴露）
- 不做自动化部署（v1.12：本期交付到"镜像已推送到镜像仓库"为止，"把镜像拉到某台服务器跑起来"
  属于部署动作，由部署方的调度器或人工完成，不由本项目流水线负责）

### 2.3 技术约束
- 开发语言：Python 3.11 及更高版本（复用团队现有技术栈）
- 部署环境：公司内网服务器（Docker 容器化部署）
- 外部依赖：GitHub API、飞书开放平台 API、公司邮件服务（SMTP）
- 运行方式：日报生成为基于 Cron 的定时任务，不需要常驻后台服务；
  展示页（v1.2）按需在本机启动一个只读的本地网页服务，用完即关，不参与定时任务链路
- 数据存储：本地 SQLite（仅用于存储日报历史记录，不需要部署远程数据库；v1.2 展示页直接读取该库，不新增数据源）
- 持续集成与交付平台：GitHub Actions（仓库已在 GitHub，无需自建流水线机器）
- 镜像仓库：GitHub Container Registry（`ghcr.io`），鉴权复用工作流自带的 `GITHUB_TOKEN`
- 镜像构建：仓库内 `Dockerfile` 多阶段构建，基础镜像 `python:3.11-slim`

## 3. 验收标准

### 3.1 功能验收
- [ ] 能够准确获取指定 GitHub 仓库过去 24h 内所有成员的 Commit 记录
- [ ] 能够准确获取「我负责的」飞书任务中当日有新建 / 完成 / 更新的那些（v1.16 口径；旧写法"当日发生状态变更的任务"依赖不存在的状态流转数据）
- [ ] 能够从飞书群消息中筛选并提取包含指定关键词的讨论记录
- [ ] 生成的日报必须包含"代码提交""任务进展""协作沟通"三个核心板块
- [ ] 日报 Markdown 格式规范，可直接渲染为高可读性的 HTML 页面
- [ ] 邮件发送链路畅通，团队 Leader 能成功接收到 HTML 格式日报
- [ ] 飞书机器人能够成功将日报推送至指定群组
- [ ] 日报中包含每位成员的当日工时和出勤状态（新增 v1.1）
- [ ] 考勤数据不可用时，日报对应字段应明确标注"考勤数据暂不可用"（新增 v1.1）
- [ ] 展示页首页能列出数据库中已有的全部日报，按日报日期倒序排列，每项显示日报日期、团队名称与生成时间（新增 v1.2）
- [ ] 点击首页任一条目能进入详情页，详情页展示该日完整日报：总览统计 + 每位成员的"代码提交/任务进展/考勤/协作沟通"四段（新增 v1.2）
- [ ] v1.2 之前生成、未记录数据源状态（`sources` 为空）的历史日报，列表与详情页标注"未记录数据源状态"，不得误报为"数据源全部失败"（新增 v1.2）
- [ ] 详情页中，当日采集失败的数据源必须标注"数据获取失败"，且与"今日无记录"在视觉上明确区分（新增 v1.2）
- [ ] 成员当日无考勤记录时，详情页对应字段显示"考勤数据暂不可用"（新增 v1.2）
- [ ] 数据库为空时，首页显示空态提示，而不是报错或白屏（新增 v1.2）
- [ ] 指定日期在数据库中无记录时，详情页显示"该日期没有日报记录"，而不是空白页（新增 v1.2）
- [ ] 日报"代码提交"段每条记录只呈现**提交标题 + 正文摘要**，不得把整段提交正文（多行清单/规范链说明）原样贴入（新增 v1.5）
- [ ] 提交正文为空（例如 GitHub 网页端上传文件产生的提交）时，只显示标题，不出现空占位或串行（新增 v1.5）
- [ ] 邮件日报以"卡片 + 配色"的可视化版式呈现：标题区、当日概览（代码提交/任务更新/协作讨论三项计数）、今日总结、按成员分组的核心板块（新增 v1.6）
- [ ] 概览计数与今日总结句必须由当日真实数据汇总得出，不得由 AI 生成，也不得出现未采集的指标（新增 v1.6）
- [ ] 邮件版式兼容主流邮件客户端：卡片与配色用表格布局 + 内联样式表达，不引用外部图片、外部 CSS 或 Web 字体（新增 v1.6）
- [ ] 邮件日报新增"今日工程进展"板块，数据取自**日报所在代码仓库本身**（本地 Git 历史）：当日提交数、迭代版本号、变更起点层级、当日被改动的规范文件、规范与代码是否在同一个提交、规范覆盖率（新增 v1.8）
- [ ] 工程进展板块的每一项都必须来自**可复现的客观事实**（本地 Git 历史 + 规范覆盖率的静态统计），不得由 AI 生成，不得现场执行测试或给出估算值（新增 v1.8）
- [ ] 变更起点层级按"受影响的最上游规范层"判定：改动 proposal 记**需求变更**；只改 design/contracts 记**设计变更**；只改 tasks 记**任务变更**；只改代码与测试记**缺陷修复**（新增 v1.8）
- [ ] 本机取不到仓库信息（非 Git 仓库、当日无提交）时，该板块显示"今日未记录工程进展"，不报错、不影响其他板块与其他数据源状态（新增 v1.8）
- [ ] 邮件主题可按配置模板渲染（默认 `{报告名} {日期}`），支持"{年级}{姓名}{日期}智能日报"这类格式 —— 占位符之间要不要分隔符由模板自己写（新增 v1.8；v1.11 起本项目采用直连形式，不再夹 `+`）
- [ ] 同一封邮件里，**正文标题区的标题必须与邮件主题一致**：收件人在收件箱里看到的名字，与点开后在正文最上方看到的名字不能是两个不同的字符串（新增 v1.11）
- [ ] 「协作沟通」只呈现**真人**发送的消息；应用自身（机器人）推到群里的内容不计入协作沟通，即使它命中了关键词（新增 v1.8.3）
- [ ] 邮件日报的「今日概览」下方有一行**当日代码变更行数汇总**：按当日全部提交的新增/删除行数求和，显示"当日代码变更 +N / -M 行"（新增 v1.9）
- [ ] 当日没有代码提交时，该行显示 `+0 / -0 行`，不隐藏、不留白（新增 v1.9）
- [ ] 日报各板块的空态必须说清"空的是什么"（代码提交＝当日无代码提交、任务进展＝当日无任务新建、更新或完成、协作沟通＝当日无符合条件的讨论、考勤＝当日无打卡记录），不得再用一句通用的"今日无记录"打发（新增 v1.10；任务口径随 v1.16 调整）
- [ ] 「今日工程进展」在当日提交数为 0 时，必须给出**最近一次提交的日期**（取自本地 Git 历史），使"今天没动"与"很久没动"能区分开（新增 v1.10）
- [ ] 上述空态文案与最近一次提交日期都必须来自确定性模板句或本地 Git 事实，不得由 AI 生成、不得估算（新增 v1.10）
- [ ] 每次 push 与 PR 自动触发流水线，跑完三个项目的测试与规范治理检查；任一环节失败则整条流水线失败（新增 v1.12）
- [ ] 测试未通过时**不得**构建或推送镜像：构建任务必须显式依赖测试任务（新增 v1.12）
- [ ] 打 `v*` 标签时构建镜像并推送到 GHCR，镜像标签至少包含提交哈希（前 7 位）与版本号，且推送后输出镜像 digest（新增 v1.12）
- [ ] 镜像以非 root 用户运行，且镜像内不含 `.env`、`config.yaml`、`data/` 等凭据与本地数据（新增 v1.12）
- [ ] 流水线全程不向真实飞书群或真实邮箱发信（只跑演示/离线模式），日志中不出现任何明文密钥（新增 v1.12）
- [ ] 邮件日报在「今日工程进展」之后新增「交付流水线」板块：用"测试门禁 → 镜像构建 → 发布到镜像仓库 → 部署（本期不做）"一条链路说清交付走到了哪一步（新增 v1.13；v1.16 起由 `email.show_pipeline` 开关控制，默认**不展示**）
- [ ] 该板块的每一项状态只能来自**仓库里的真实文件与 Git 事实**（工作流文件名、`Dockerfile` 的阶段数/`USER`/`HEALTHCHECK`、`git tag`）；采集不到就写"未采集"并说明原因，**不得**把没验证过的事写成"已跑通"（新增 v1.13）
- [ ] 「交付流水线」只在邮件渠道出现，展示页保持 v1.2 的"总览 + 成员四段"不变（新增 v1.13）
- [ ] 非工作日（双休日或配置的法定节假日）两侧都没有打卡时，考勤状态显示「休息日」而不是「缺勤」；工作日两侧都缺仍判「缺勤」（新增 v1.13）
- [ ] 「交付流水线」板块的「最近一次运行」显示**真实结论**：读默认分支最新提交的 Check Runs（GitHub 公开接口，无需带 `actions:read` 的令牌），聚合为「成功 / 失败 / 进行中」之一（新增 v1.14）
- [ ] 该结论必须附提交哈希前 7 位，让收件人能拿这串哈希原样回查；只有结论没有哈希等于不可复核（新增 v1.14）
- [ ] 结论的判定口径固定：任一检查项的结论不属于 `success/neutral/skipped` 即「失败」；全部已完成且无失败即「成功」；存在未完成的检查项即「进行中」，**不得**与"成功"混同（新增 v1.14）
- [ ] 没有 Check Run、接口不可达、超时、限流或没有配置仓库标识时，写「未采集（公开 Check Runs 接口读不到）」，**不得**臆测为成功或失败（新增 v1.14）
- [ ] 「最新版本标签」改为**远端优先**：先读仓库远端的 `v*` 标签（公开接口），取不到再回退本地 `git tag`；两者都没有时该行不出现。该行只表示"仓库上最新的版本标签"，不宣称镜像已按该标签发布（新增 v1.14）
- [ ] 上述网络取数必须带超时，且任何一个取不到都只影响该行显示，日报照常生成、照常推送（新增 v1.14）
- [ ] 邮件日报的「代码提交」板块只保留"本日在某仓库共提交 N 次，累计 +X/-Y 行"这一句汇总，**不再**逐条列出主要变更（新增 v1.15；逐条明细仍保留在飞书 Markdown 日报）
- [ ] 邮件日报的成员分组只呈现代码提交、任务进展、考勤三块，**不再**出现「协作沟通」板块（新增 v1.15；该板块仍保留在飞书 Markdown 日报与展示页）
- [ ] 任务进展板块必须呈现**真实任务本身**：任务标题 + 日期 + 完成情况（「已完成 10-24」/「未完成」）；日期取任务创建时间，已完成的补完成时间（新增 v1.16）
- [ ] 任务只采「我负责的」（`GET /task/v2/tasks?type=my_tasks`），且必须用**用户身份** `user_access_token`：应用身份调用不报错但恒返回 0 条，与"今天真的没任务"无法区分（新增 v1.16）
- [ ] 未完成用户授权时必须**明确失败**并给出一次性授权命令（`python main.py --lark-auth`），**不得**把"读不到"渲染成"今日无任务"（新增 v1.16）
- [ ] 任务窗口口径：`created_at` / `completed_at` / `updated_at` 任一落在当日窗口内才计入（新增 v1.16）
- [ ] 「交付流水线」板块改为开关控制（`email.show_pipeline`，**默认关闭**）：关闭时不采集（连那两次 HTTP 都不发）、不渲染，邮件里连板块标题都不出现（新增 v1.16）
- [ ] 开关打开时，「交付流水线」的行为与 v1.14 完全一致，不得因这次改动退化（新增 v1.16）
- [ ] 授权失败时必须说清**飞书自己给的原因**（如「授权码已过期」「redirect_uri 不合法」），不得只显示一个空原因；授权回调走不通时，提供"把 API 调试台拿到的 `user_access_token` 直接交给程序"的备用通道（`python main.py --lark-user-token <TOKEN>`），并在输出里写明它 2 小时失效、没有 refresh_token（新增 v1.16.2）
- [ ] 只有 1 个成员的日报，邮件正文**不出现成员名条**（如「我（网页端）」）：主题与标题区已经表明这是谁的日报，正文再标一次只是噪音；成员 ≥2 时名条必须保留（新增 v1.17）
- [ ] 邮件里「今日工程进展」排在**全篇最后**（成员分组之后）：收件人的阅读顺序是"今天我做了什么"→"项目整体到哪一步"（新增 v1.17）
- [ ] 多成员日报必须渲染**每一个**成员：不得因循环里的提前 `return` 只渲染第一个人（v1.15 引入的缺陷，v1.17 修复；当年单成员配置掩盖了它）（新增 v1.17）
- [ ] 邮件标题区必须让**日期一眼可见**：标题行之下单独一行"日期胶囊"（深青底、白字），内容为 `YYYY-MM-DD` + 中文星期；日期不得只藏在主题串里（新增 v1.18）
- [ ] 标题区右侧的"生成于"只写**时分**（`14:01`）；仅当生成日与日报日不是同一天时才写完整 `YYYY-MM-DD HH:MM`，避免重复又不失真（新增 v1.18）
- [ ] 标题区改版不得改动主题串（主题仍与 `email.subject_pattern` 同源），也不得新增色板以外的颜色（新增 v1.18）

### 3.2 性能验收
- [ ] 单次日报生成耗时（以 5 人团队为例）< 60s
- [ ] 单一数据源（如某 API）超时或失败，不应阻断其他数据源的采集
- [ ] 采集失败的数据源需要在日报中显式标注"数据获取失败"，严禁静默跳过
- [ ] 展示页首页在数据库存有 365 条日报时，首次加载完成耗时 < 2s（新增 v1.2）
- [ ] 展示页详情页单次请求响应耗时 < 1s（新增 v1.2）
- [ ] 流水线单次运行（三个项目测试 + 规范治理）在 10 分钟内完成；命中依赖缓存时不超过 5 分钟（新增 v1.12）

### 3.3 边界场景
- [ ] 若团队成员当日无任何提交、任务或消息，日报对应板块应给出该板块自己的空态说明（如"当日无代码提交"），不得留白（v1.10 起不再统一写"今日无记录"，见 §3.1）
- [ ] 当 GitHub API 触发限流时，系统应具备等待并重试机制（上限三次）
- [ ] 当飞书 Token 过期时，系统应能自动刷新 Token
- [ ] 双休日与法定节假日同样可以正常生成、推送日报，不得因为"今天不是工作日"而拒绝运行（变更 v1.4）
- [ ] 仅当显式开启"仅工作日"模式（`--working-days-only`）时，才在周末或配置的
      法定节假日跳过日报生成，并明确打印跳过原因（变更 v1.4）
- [ ] 展示页服务仅监听本机回环地址，同一局域网内其他机器无法访问（新增 v1.2）
- [ ] 展示页收到未实现的方法（如对页面地址发起写操作）时返回明确错误，不产生任何数据变更（新增 v1.2）
- [ ] 数据库中某条日报的日报日期格式异常时，该条记录在首页被跳过并记录日志，不影响其余记录正常列出（新增 v1.2）
- [ ] 容器镜像内取不到 Git 历史（镜像不包含 `.git`）时，「今日工程进展」降级为中性空态「今日未记录工程进展」，不得报错、不得影响其余板块与推送（新增 v1.12）
- [ ] 镜像仓库不可用或鉴权失败时，流水线明确失败并在日志里指出是"登录失败"还是"推送被拒"，不静默跳过发布（新增 v1.12）
- [ ] 本机取不到仓库信息、或仓库里没有流水线文件时，不报错、不影响其他板块与推送（新增 v1.13；v1.16 起该板块默认关闭，关闭时连板块标题都不出现，不再显示"未记录交付流水线"）
- [ ] 读流水线运行结论的接口超时、被限流（403/429）或返回异常结构时，「最近一次运行」降级为「未采集（公开 Check Runs 接口读不到）」，日报照常生成与推送，不重试到拖垮整次执行（新增 v1.14）
- [ ] 邮件渠道不再展示「协作沟通」后，飞书消息采集失败仍必须在顶部的来源告警里如实列出，不得因为"不展示了"就把采集失败藏起来（新增 v1.15）
- [ ] 读任务的用户身份 Token 过期或缺失时，日报顶部来源告警必须标出「飞书任务」失败及原因，且给出可执行的授权指引；不得让整次日报失败（新增 v1.16）

## 4. 术语定义
| 术语     | 定义                                                                 |
|----------|----------------------------------------------------------------------|
| 日报     | 系统自动生成的每日工作摘要，涵盖代码、任务、沟通三个维度             |
| 成员     | 已在系统中完成 GitHub 与飞书账号映射绑定的团队成员                   |
| 数据源   | 提供原始工作数据的外部协作平台（GitHub、飞书任务、飞书消息）         |
| 采集窗口 | 单次采集所覆盖的时间跨度，默认为当日 00:00 至任务执行时刻            |
| 展示页   | v1.2 新增：在本机浏览器中只读浏览已生成日报的本地网页，不参与日报生成与推送 |
| 工程数据源 | v1.8 新增：日报所在代码仓库本身（本地 Git 历史与规范文件）。它**不是**外部协作平台，因此不参与"数据源状态"（sources）的四态判定，只在邮件的"今日工程进展"板块呈现 |
| 持续集成（CI） | v1.12 新增：每次推送后由流水线自动完成的"验证"环节（装依赖、跑测试、跑规范治理），产出的是红/绿结论，不产出制品 |
| 持续交付（CD） | v1.12 新增：验证通过后自动产出可部署制品（容器镜像）并推送到镜像仓库。本期到"镜像已发布"为止，**不含**自动部署 |
| 镜像与 digest | v1.12 新增：镜像即"代码 + 依赖 + 运行方式"的打包结果；digest（`sha256:…`）是镜像内容的唯一指纹，部署与回滚都应锁定 digest 而不是 `latest` |
